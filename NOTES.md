# VANTRA — NOTES: what is simulated, what is real, what is descoped

## What is simulated vs real

| Component | Status | Notes |
|---|---|---|
| Camera network (18 nodes, Bengaluru) | **Simulated** | Coordinates are real Bengaluru locations (MG Road, Indiranagar, Koramangala, Silk Board…), but adjacency/distance/speed limits are hand-modeled approximations of the road graph (haversine × 1.35 road factor). Swap-in: import cameras + a routable edge graph from OpenStreetMap (OSMnx) or a feed of real camera GPS positions. |
| Historical detection logs (23k detections / 21 days) | **Simulated** | Generated by `app/ml/simulator.py` with realistic noise: OCR errors via a visually-confusable character model, per-pass 6% camera miss rate, dwell stops at stop-eligible edges, peak-hour congestion. Ground truth (true plate, true camera, session id) is retained in `plate_correct` / `gt_cam` / `session_id` columns — these would not exist in production. |
| Plate/vehicle images | **Synthetic** | Rendered programmatically (`app/ml/imagegen.py`): Indian plate formats (KA/BH RTO codes, commercial yellow), simple vehicle sprites, controlled degradations (motion blur, rotation/squeeze, low light + noise, dirt occlusion, rain streaks). |
| OCR engine | **Real code, synthetic-domain** | A working pipeline: contrast-based plate localization + multi-threshold segmentation + per-glyph template matching, with Otsu adaptive binarization, deskew/x-stretch variants, and calibrated confidence. It genuinely degrades on the stress conditions and the metrics are honestly measured. It is NOT a trained deep model. |
| Re-ID embeddings | **Real code, handcrafted features** | Deterministic descriptor: hue histogram + color-class one-hot + vehicle-type one-hot + saturation/value stats, cosine similarity. Same-vehicle 0.93+, different-vehicle ≤0.63 on our data. |
| Travel-time distributions | **Learned (from simulated data)** | Percentiles (p5/p50/p95) fitted per edge from the simulated ground-truth consecutive passes, both direct (1-hop) and skip-one (2-hop). The fitting code (`scripts/seed_history.py: fit_travel_time_stats`) is production-shaped — point it at real logs and it works unchanged. |
| Trajectory matcher, alerts, analytics, dashboard | **Real** | The core logic runs as written; no stubs. |

## Stand-ins for production ML components

The architecture deliberately keeps ML models behind narrow interfaces so the
hackathon-scale stand-ins can be swapped without touching the matching layer:

- **Plate detection (YOLOv8)**: `app/ml/ocr.py:detect_plate_box` (contrast-box
  scan). Production: fine-tune YOLOv8 on a plate-detection dataset (e.g. CCPPD,
  Indian plates from Kaggle); replace this one function — it returns a bbox, same
  contract.
- **OCR (text recognition)**: REAL, FINE-TUNED — `app/ml/ocr.py:read_plate`
  runs EasyOCR (pretrained CRAFT+CRNN) with recognition weights fine-tuned on
  7,318 real plates from two public datasets (+augmentation = 29,272 rows).
  Held-out real-world result: 47.9% exact / 78.3% char accuracy (vs 0% /
  1.6% for the original template matcher, 1.9%/37.5% for stock pretrained).
  Full dataset/split/iteration/error analysis in docs/REALWORLD_OCR.md. The
  ~48% is a data-size ceiling (val plateau across 4 hyperparameter runs);
  closing to >90% needs 10-50x more labeled plates (CCPD-scale), super-res for
  <80px crops, and perspective rectification for oblique plates. The old
  template matcher remains as `_read_plate_template` fallback when the model
  is unavailable (CI).
- **Vehicle Re-ID (VeRi-776 model)**: `app/ml/reid.py:embed` (color/shape
  descriptor). Production: a CNN re-ID embedding trained on VeRi-776/VehicleID
  (e.g. fast-reid); returns an L2-normalized vector, same contract. The matcher's
  `appearance_floor` / `appearance_margin` thresholds would need retuning per
  model.

## Trajectory view geometry

Trajectories draw straight edges between camera nodes (map polylines). No OSRM
road-snapping is wired in. Swap-in: run a local OSRM server, request the route
between consecutive camera coordinates, and feed the polyline geometry to the
dashboard. The PDF case file already attempts to fetch real OSM tiles for its map
snapshot and falls back to a schematic when offline.

## Production-scale architecture (designed, not built)

The current pipeline is in-process and synchronous. At city scale:

- **Ingestion**: per-camera RTSP frames → Kafka topic. A GPU worker pool runs
  detection + OCR + Re-ID per frame group; detections published to a
  `detections` topic. (The `/api/ingest` endpoint is the architectural stand-in
  for this boundary.)
- **Async tasks**: Celery/RQ (or Kafka Streams) for trajectory stitching and
  alert evaluation as streaming jobs over the detection topic, keyed by plate
  so all sightings of a plate hit the same worker.
- **Storage**: PostgreSQL + PostGIS is retained for cameras/edges/trajectories
  (it already uses PostGIS points and (plate, ts)/(camera_id, ts) indexes). Raw
  detections at city scale move to a time-series store (TimescaleDB with
  hypertables on `ts`, or ClickHouse) with hot/cold tiering; crops go to object
  storage (S3) instead of local disk.
- **Travel-time model**: refit nightly (the fitting code is already batch-shaped);
  at scale, per-edge per-hour-of-day distributions rather than one per edge.
- **Serving**: read replicas for the dashboard API; alerts pushed over WebSocket.

## Explicitly descoped / stretch features

- **Soft anomaly (per-plate statistical pattern)**: implemented
  (`app/services/alerts.py: soft_anomalies` — circular time-of-day z-score +
  route novelty against the plate's own history) but **not wired to live
  ingestion**; it runs on demand. The simulated per-plate history (commuters with
  ~40 observations) is enough to demo it but thin for confident statistics.
  Production: needs months of history and a proper per-plate behavioral model
  (e.g. per-plate camera-visit histogram + time-of-day mixture model).
- **Convoy detection**: implemented over the watchlist (blacklist doubles as the
  watchlist). Not exercised in the six demo scenarios (no convoyed pair seeded).
- **Hop skipping beyond one camera**: the matcher widens across exactly 2 hops
  (one missed camera). Two consecutive misses break the trajectory by design —
  confidence in a 3-hop guess would be too low to act on.
- **Video ingestion (rigor pass)**: the live dashboard now has a second mode
  ("Video pipeline") that decodes a bundled mp4 traffic clip and runs the REAL
  detect+OCR+embedding pipeline per sampled frame. Honest numbers: ~0.6 fps
  effective processing rate vs the clip's native 10 fps (single-core template
  matching, ~1.5–3 s/frame) — the UI displays the real rate. The clip itself is
  synthetically rendered (`scripts/make_traffic_video.py`) because no real
  dashcam footage is bundled with the repo; the pipeline is format-agnostic
  H.264/mp4 and would run unchanged on real footage. JSON replay remains the
  default live mode. Production: real RTSP ingestion + GPU inference as per the
  architecture doc.

## Known limitations / honest numbers

- OCR on heavy motion blur and viewing-angle stress is poor (28% / 8% exact) —
  reported honestly in docs/METRICS.md. The confidence signal correctly marks
  those reads as unreliable (mean conf 0.43 / 0.53), and the matcher's
  appearance+route tiers carry those hops instead.
- Stitching with 0 misses measured 85% vs 94% with 1 miss — small-sample noise
  (20 vs 18 trials), not a real inversion; both round to "high single-digit
  failure rate", dominated by long-dwell hops falling outside even the widened
  window.
- The evaluation datasets are synthetic; the numbers validate the *logic*, not
  real-world accuracy.

## VLM-fallback pass (negative result, kept toggleable)

`app/ml/ocr.py:read_plate` supports an optional second-opinion escalation to a
multimodal model (gemini-3.7-flash via the latentcode gateway) when the CRNN
read's confidence is below `VANTRA_VLM_THRESHOLD`. **Off by default** — on the
held-out real-world test the combined pipeline scored *below* CRNN-alone
(46.2-47.0% vs 47.9%): the VLM overwrites more correct CRNN reads than it
recovers missed ones (165 lost vs 30 gained). Full 9-configuration grid,
overlap analysis, and cost model in docs/REALWORLD_OCR.md. The path may become
useful for conditions the CRNN cannot represent (non-Latin scripts, multi-line
plates); enable with `VANTRA_VLM_FALLBACK=1` + a latentcode key.

## Accuracy-push pass (negative result, r5 not deployed)

Tripled the real-plate corpus (21,154 crops incl. 12,590 Chinese) + ESPCN SR
copies; trained r5 to full convergence (val plateau ~48%, 6 epochs). Held-out
dropped to 45.3% (vs r3's 47.9%) from Chinese-plate domain shift; SR did not
move the small-crop bucket. **r3 remains the production model.** Available
public labeled real-plate data is effectively exhausted (survey documented in
REALWORLD_OCR.md). Next real lever: per-country model routing or a transformer
recognizer head (PARSeq-class) — out of scope for CPU training here.
